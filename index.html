Synthesized Recommendations

from both machines

1. Front-Load Diagnostics (Biggest ROI)

Wrong-approach is your #1 combined friction. Before implementing any fix, have Claude list 3 possible root causes ranked by likelihood with falsification criteria. Investigate the most likely one for no more than 5 minutes before reassessing. This alone could save hours weekly.

Before implementing a fix, list 3 possible root causes ranked by likelihood. For each, describe what evidence would confirm or rule it out. Then investigate the most likely one first, spending no more than 5 minutes before reassessing.

2. Deployment Protocol (Pre-Flight + Verification)

110 deployment-related issues on studio, plus CDN caching, stale deploys, and session collisions on laptop. Always run vercel env ls before deploy, check vercel.json for redirect conflicts, and smoke test after every deployment. Never fire-and-forget.

Before deploying: 1) vercel env ls — compare against local .env, flag missing vars. 2) Check vercel.json for conflicting redirects. 3) After deploy, wait 30s for CDN, then curl the live URL and verify expected content. 4) If stale, vercel --prod --force. 5) Report: URL, status code, git SHA deployed.

3. Session Handoff Protocol

19+ sessions spent on status reconstruction. Standardize a HANDOFF.md that auto-generates at session end: current branch, last deployment URL, blockers, next steps. Every new session starts by reading it.

Before ending this session, create HANDOFF.md with: ## Current State (branch, last commit SHA, deployment URL), ## Completed This Session (bullets), ## Blockers (issues + diagnosis), ## Next Steps (prioritized). Commit and push.

4. API Auth Protocol

Read API docs before implementing authentication. Verify: timestamp format, message structure, all headers. If auth fails 3+ times, rebuild from scratch. For npm: always use .npmrc token auth. Never attempt recovery codes as OTP.

Before testing this API integration: walk me through exactly how the request signing works — show timestamp format, exact string being signed, all headers being sent. Compare each against the API documentation. If auth fails 3 times, rebuild from scratch.

5. Multi-Session Isolation

Parallel sessions deploying to the same project causes constant collisions. Each agent session should: check current git branch, confirm repo, never assume its deployment is latest. Write to AGENTS.md before deploying.

Before editing: verify git branch and confirm repo directory. Before deploying: check AGENTS.md for in-flight deploys. After deploying: write your agent ID, deployment URL, and timestamp to AGENTS.md. If detect deploy conflict, wait 60s and retry.

6. Don't Re-Verify Completed Work

Multiple sessions showed Claude re-verifying already-confirmed work, leading to interruptions and frustration. When the user says it's done, accept the confirmation and move to the next task immediately.

Autonomous Deploy-Test-Fix Loops

Instead of manually catching deploy failures, agents run in tight loops: deploy, end-to-end test against production, diagnose failures, fix, redeploy — iterating autonomously until all checks pass. The npm publish saga and artifact 404 debugging would each resolve in minutes.

Create scripts/verify-deploy.sh that hits production endpoints and returns structured pass/fail JSON. Loop: deploy → verify → diagnose → fix → redeploy. Max 5 iterations as safety valve.

End every session by updating PROJECT_STATUS.md with structured sections. Claude Code's auto-memory + CLAUDE.md conventions make this achievable today.
